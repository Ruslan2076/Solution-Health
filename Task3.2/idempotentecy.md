# Задание 3.2. Механизм обеспечения идемпотентности на входе

## Проблема

API Расписания не отличает повторный запрос от нового: повторный POST создаёт вторую запись (INT-005). Двойное нажатие кнопки «Записаться» приводит к двум записям (SD-003), и такие дубли составляют значительную часть обращений в контакт-центр. У мобильного клиента повторы происходят чаще, чем у веб-портала: двойное касание, повторная отправка при обрыве связи в метро или лифте, автоматический повтор запроса приложением или шлюзом после таймаута. Пока входная операция не идемпотентна, повторы нельзя включать вообще, а без них теряется устойчивость к сетевым сбоям.

## Механизм

### Ключ идемпотентности

Мобильное приложение формирует Idempotency-Key в виде UUID **в момент, когда пациент начинает оформление записи**, и хранит его вместе с черновиком записи локально. Ключ передаётся в заголовке `Idempotency-Key` во всех попытках отправки этой записи, включая автоматические повторы после таймаута и повторные нажатия кнопки. Новый ключ создаётся только тогда, когда пациент осознанно начинает новое оформление: вернулся к выбору слота, изменил врача, время или состав анализов. Ключ, сформированный на момент отправки запроса, эту задачу не решает, потому что при повторном нажатии он оказался бы новым.

### Проверка на API Gateway

API Gateway отклоняет изменяющие запросы без заголовка `Idempotency-Key` кодом 400 и передаёт ключ дальше вместе с traceId. Так требование распространяется на всех клиентов, включая веб-портал, и не зависит от реализации конкретного приложения.

### Журнал идемпотентности в оркестраторе

Сервис онлайн-записи ведёт журнал идемпотентности со следующими полями: ключ, идентификатор пациента, отпечаток тела запроса, идентификатор экземпляра Saga, статус обработки, сохранённый ответ, время создания. Ключ уникален в пределах пациента, поэтому ключ, сформированный одним пациентом, не влияет на записи другого.

Запись в журнал выполняется в одной транзакции с созданием экземпляра Saga. Уникальный индекс по паре «пациент + ключ» гарантирует, что при одновременном приходе двух запросов с одним ключом экземпляр Saga создаст только один из них, а второй получит ошибку уникальности и перейдёт к обработке повтора.

### Обработка запроса

| Состояние ключа в журнале | Ответ | Пояснение |
|---|---|---|
| Ключ отсутствует | 202 Accepted с идентификатором экземпляра Saga | Создаётся новый экземпляр Saga, запись в журнал выполняется в той же транзакции |
| Ключ найден, обработка выполняется | 202 Accepted с тем же идентификатором экземпляра Saga | Повтор во время выполнения не создаёт вторую запись, клиент продолжает опрашивать статус |
| Ключ найден, обработка завершена | Сохранённый ответ первой попытки | Ответ отдаётся без повторного выполнения операции |
| Ключ найден, тело запроса отличается | 422 с описанием расхождения | Ключ переиспользован с другими параметрами. Это ошибка клиента, а не повтор |

Отпечаток тела запроса считается по значимым полям: идентификатор слота, врач, время, состав анализов, способ оплаты. Поля, не влияющие на результат, в отпечаток не входят.

Срок хранения записей журнала — 24 часа. Этого достаточно, чтобы покрыть все повторы одной попытки записи, включая возврат пациента к приложению после долгой потери связи, и при этом журнал не растёт бесконечно.

### Идемпотентность шагов внутри Saga

Ключ на входе защищает от дублирующей записи целиком. Отдельно защищается каждый изменяющий шаг: оркестратор формирует ключ шага из идентификатора экземпляра Saga и номера шага и передаёт его участнику. Участник сохраняет результат по ключу и при повторном вызове возвращает сохранённый ответ, не выполняя операцию заново.

| Шаг | Ключ шага | Что защищает |
|---|---|---|
| Удержание слота | sagaId + номер шага | Повтор не создаёт второе удержание того же слота |
| Резервирование окна забора | sagaId + номер шага | Повтор не занимает второе окно в лаборатории |
| Авторизация платежа | sagaId + номер шага, передаётся платёжному шлюзу | Повтор не блокирует сумму дважды |
| Подтверждение слота и окна | sagaId + номер шага | Повторы этого шага безопасны, поэтому шаг относится к повторяемым |
| Списание средств | sagaId + номер шага, передаётся платёжному шлюзу | Повтор не списывает деньги дважды. Автоматический повтор списания не выполняется, но ключ страхует от повтора, инициированного вручную или сетью |
| Компенсации | Идентификатор компенсируемой операции (holdId, labBookingId, authId) | Повторная компенсация не снимает резерв повторно и не создаёт второй отмены авторизации |

### Идемпотентность потребителей событий

События Saga доставляются через Kafka с гарантией at-least-once, поэтому потребители отсекают повторы по eventId: Уведомления не отправляют второй push о подтверждении записи, CRM не создаёт вторую запись в истории обращений.

## Что устраняет механизм

| Ситуация | Поведение системы |
|---|---|
| Пациент дважды нажал «Записаться» | Второй запрос приходит с тем же ключом и получает идентификатор того же экземпляра Saga. Создаётся одна запись |
| Связь оборвалась, приложение повторило запрос | Тот же ключ, тот же экземпляр Saga. Пациент видит статус первой попытки |
| Запрос дошёл до сервера, ответ не дошёл до клиента | Повтор возвращает сохранённый ответ первой попытки, вторая запись не создаётся |
| Оркестратор повторил вызов участника после таймаута | Ключ шага не даёт участнику выполнить операцию второй раз |
| Пациент изменил время приёма и отправил запись заново | Приложение формирует новый ключ, создаётся новая запись. Прежняя не затрагивается |
| Kafka доставила событие о подтверждении дважды | Уведомления отсекают повтор по eventId, пациент получает один push |
