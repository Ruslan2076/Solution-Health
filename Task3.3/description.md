# Задание 3.3. Комментарий к спецификации API мобильного приложения

Спецификация: `Задание_3_3_appointments_openapi.yaml` (OpenAPI 3.2.0).

## Ресурс и метод

| Элемент контракта | Решение |
|---|---|
| Ресурс | `/appointments` — существительное во множественном числе, без глаголов в пути |
| Метод | `GET`: операция не меняет состояние, безопасна и идемпотентна, поэтому повтор после таймаута безвреден и запрос кешируется |
| Базовый URL | `https://api.zdorovie-plus.ru/api/v1` |
| Структура ответа | Объект с полями `items` и `pagination`, а не голый массив. Массив верхнего уровня нельзя расширить, не сломав клиентов, а объект допускает добавление полей |
| Формат ошибки | Единый объект с полями `code`, `message`, `traceId` для всех кодов ошибок |

Идентификатор пациента в запросе не передаётся: он читается из поля `sub` токена доступа. Параметр вида `patient_id` в query позволил бы запросить чужие записи подбором идентификатора, поэтому его в контракте нет.

## Пагинация

Выбрана схема `limit` и `offset`.

| Параметр | Значение по умолчанию | Ограничения |
|---|---|---|
| `limit` | 20 | от 1 до 100 |
| `offset` | 0 | не меньше 0 |

Ответ содержит объект `pagination` с полями `total`, `limit`, `offset`, `next` и `prev`. Поля `next` и `prev` принимают значение `null` на границах выборки, поэтому приложению не требуется самостоятельно вычислять, есть ли следующая страница.

**Почему limit и offset.** Набор данных здесь небольшой и ограничен одним пациентом: предстоящих записей единицы, а вся история за несколько лет измеряется десятками. Глубокие смещения, на которых offset-пагинация деградирует, в этом сценарии не возникают: база не окажется в ситуации, когда для выдачи 20 записей нужно прочитать сто тысяч. Второй недостаток offset-пагинации — пропуски и дубли при изменении данных между запросами — также ограничен: записи пациента меняются его собственными действиями, а не потоком событий, и выборка отсортирована по времени приёма, а не по времени создания. Поле `total` позволяет приложению показать общее число записей, что при курсорной пагинации потребовало бы отдельного запроса.

**Почему не курсорная пагинация.** Курсор даёт постоянную скорость на любом объёме и устойчивость к изменениям данных, но не позволяет перейти на произвольную страницу и усложняет клиент. Для списка записей одного пациента эти преимущества не востребованы, а цена в виде усложнения контракта платится сразу. Для эндпойнтов с большими и динамичными выборками — например, журнала операций или списка результатов анализов за всё время — курсорная пагинация остаётся предпочтительным вариантом, и переход на неё выполняется добавлением параметра `cursor` без удаления `limit` и `offset`, то есть без мажорной версии.

**Почему не page и per_page.** Схема эквивалентна по смыслу, но `limit` и `offset` выбраны как единая конвенция для всех эндпойнтов API, чтобы потребителям не приходилось помнить разные наборы параметров.

## Фильтрация

| Параметр | Назначение |
|---|---|
| `status` | Состояние записи: `upcoming`, `completed`, `cancelled`. Значение по умолчанию — `upcoming`, поэтому главный экран приложения получает нужные данные без передачи параметров |
| `date_from`, `date_to` | Границы периода по времени начала приёма |

Несколько значений статуса передаются повторением параметра: `?status=upcoming&status=cancelled`. Перечисление в `enum` даёт валидацию на стороне шлюза и подсказки в сгенерированной документации. Диапазон дат задан парой параметров с суффиксами, что соответствует общей конвенции API для диапазонов.

Пример запроса главного экрана приложения:

```
GET /api/v1/appointments?status=upcoming&limit=20&offset=0
Authorization: Bearer <token>
```

## Версионирование

Версия указана в пути: `/api/v1/...`.

**Почему в URL.** Такой вариант виден в логах, в обращениях в поддержку и в отладчике, просто маршрутизируется на шлюзе и позволяет направлять трафик разных версий на разные группы экземпляров сервиса. Версионирование через заголовок `Accept` не загрязняет путь, но версия перестаёт быть видимой при разборе инцидента, а в мобильном приложении это существенно: у пользователей одновременно работают разные версии клиента, и по логу нужно понимать, какая из них сформировала запрос. Версионирование через параметр запроса нарушает кеширование и не применяется.

**Что требует новой версии.** Мажорная версия выпускается только при обратно несовместимых изменениях: удаление поля, изменение типа поля, изменение семантики значения, добавление обязательного параметра. Добавление нового поля в ответ, нового необязательного параметра или нового эндпойнта выполняется в пределах текущей версии, поэтому приложение старой сборки продолжает работать.

**Политика устаревания.** Предыдущая мажорная версия поддерживается шесть месяцев с даты выпуска новой. Срок выбран с учётом того, что часть пациентов обновляет приложение редко, а принудительно обновить установленное приложение нельзя. Политика зафиксирована в поле `description` спецификации, а не только во внутренних документах, чтобы потребитель видел её вместе с контрактом.

## Аутентификация

Схема безопасности `bearerAuth` объявлена на уровне документа и действует на все операции. Токен доступа выдаёт Identity Provider по протоколу OIDC, формат токена — JWT. Токен передаётся в заголовке `Authorization`.

Токен вместо серверной сессии выбран потому, что сервисы остаются stateless и масштабируются горизонтально, а идентификатор пациента внутри токена подписан и не может быть подменён на стороне клиента.

## Коды ответов

| Код | Когда возвращается | Что делает приложение |
|---|---|---|
| `200` | Запрос выполнен. Пустой список записей также возвращается с кодом 200 и пустым массивом `items` | Показывает список или состояние «нет предстоящих записей» |
| `401` | Токен отсутствует, истёк или недействителен. В заголовке `WWW-Authenticate` указана причина отказа | Обновляет токен и повторяет запрос, при повторной ошибке открывает экран входа |
| `500` | Внутренняя ошибка сервиса | Повторяет запрос с экспоненциальной задержкой, поскольку `GET` безопасен, и показывает пациенту сообщение из поля `message` |

Отсутствие записей не является ошибкой, поэтому код 404 для пустого списка не используется: ресурс `/appointments` существует всегда. Ответ 200 с телом, содержащим описание ошибки, в контракте не допускается: код ответа должен отражать исход запроса, иначе клиенты и мониторинг перестают различать успех и отказ.

Каждый ответ, включая ошибочный, содержит `traceId`. Пациент может назвать его в контакт-центре, и обращение связывается с конкретным запросом в платформе наблюдаемости без разбора логов по времени.

## Примечание о версии OpenAPI

Спецификация объявлена как OpenAPI 3.2.0. Из возможностей, появившихся в этой версии, используется поле `summary` в объекте тега. Схемы описаны по JSON Schema 2020-12: необязательные поля, принимающие пустое значение, заданы через `oneOf` с типом `null`, а не через устаревшее ключевое слово `nullable`.
