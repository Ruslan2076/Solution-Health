# Задание 3.1. Надёжная поставка результатов анализов: сравнение вариантов и выбор решения

## Критерии сравнения

| Критерий | Что оценивается |
|---|---|
| Гарантия доставки | Может ли результат потеряться или задублироваться, есть ли восстановление без ручной перевыгрузки |
| Задержка | Время от статуса «готов» в LIS до появления результата в приложении |
| Пиковая нагрузка | Поведение при утреннем всплеске результатов и при волне чтений от пациентов |
| Простота эксплуатации | Сколько ручной работы требуют сбои, видны ли они без разбора логов |
| Связанность с legacy | Насколько решение зависит от внутреннего устройства и доступности LIS |

## Сравнение архитектурных вариантов

| Вариант | Гарантия доставки | Задержка | Пиковая нагрузка | Простота эксплуатации | Связанность с legacy | Решение |
|---|---|---|---|---|---|---|
| 1. Синхронная передача LIS → CRM по REST новым коннектором с повторами | Средняя. При недоступности CRM дольше бюджета повторов результат теряется, промежуточного буфера нет | Секунды | Утренний всплеск приходит напрямую в CRM | Высокая: один компонент | Временная связанность: LIS и CRM должны быть доступны одновременно | Отклонён: не обеспечивает гарантированную доставку |
| 2. Пакетная выгрузка LIS → CRM по расписанию с мониторингом и повтором пачек | Высокая | Равна интервалу выгрузки. Сокращение интервала до минут превращает пакетный обмен в частый опрос с накладными расходами пакетной обработки | Хорошо: нагрузка распределяется пачками | Низкая: регламенты запуска, ручной разбор ошибок на уровне записей | Минимальная | Отклонён: не обеспечивает минимальную задержку |
| 3. Приложение читает результаты напрямую из LIS через API Gateway | Доставки как процесса нет, данные читаются по запросу. Для уведомления о готовности нужен отдельный механизм | Нулевая | Нагрузка до 50 тыс. пользователей приходит на legacy-систему | Средняя | Сильная: LIS становится звеном синхронной цепочки для приложения, врачи в CRM по-прежнему зависят от старого канала | Отклонён: не выдерживает пиковую нагрузку |
| 4. Асинхронная очередь point-to-point в RabbitMQ: адаптер → CRM → Уведомления | At-least-once с подтверждениями и DLQ. Подтверждённое сообщение удаляется из очереди, повторное чтение невозможно | Секунды | Хорошо: брокер буферизует, prefetch ограничивает темп | Средняя. Действующий RabbitMQ уже перегружается в пиках (SD-006), нужен отдельный кластер. Новый потребитель требует новой очереди и привязки | Слабая | Отклонён: восстановление после ошибки потребителя требует перевыгрузки из LIS |
| **5. Событийная доставка через Kafka с Transactional Outbox, идемпотентными потребителями, DLQ и суточной сверкой** | **Высокая. Outbox исключает потерю между БД и брокером, события хранятся для повторного чтения, DLQ изолирует сбойные события, сверка находит пропуски на входе** | **До 2 минут, определяется интервалом опроса LIS** | **Kafka принимает всплеск, потребители читают в своём темпе, масштабирование группой потребителей по партициям** | **Средняя. Kafka требует экспертизы, но уже входит в целевую архитектуру, отдельная инфраструктура для результатов не нужна. Сбои видны по метрикам, повтор доступен из панели** | **Слабая: LIS не знает о потребителях, адаптер изолирует её протокол** | **Выбран** |
| 6. Захват изменений (CDC) из БД LIS через Debezium → Kafka | Высокая: изменения читаются из журнала БД | Секунды | Хорошо | Низкая: дополнительный кластер Kafka Connect, сопровождение коннектора | Сильная: требует доступа к журналу БД legacy-системы и привязывает интеграцию к её внутренней схеме. Изменение схемы поставщиком LIS ломает интеграцию так же, как смена формата ответа ломала интеграцию с 1С | Отклонён: связанность с внутренним устройством LIS |

Вариант 5 выбран, потому что он единственный одновременно закрывает все четыре требования. Гарантию доставки обеспечивают outbox, хранение событий, DLQ и сверка. Задержка ограничена интервалом опроса. Пиковую нагрузку поглощает брокер. Эксплуатация опирается на метрики и панель повторной отправки вместо ручных перезапусков. Вариант 4 близок по свойствам, но без повторного чтения событий восстановление после ошибки потребителя требует ручной перевыгрузки из LIS, а именно такую ручную работу решение должно устранить.

## Сравнение инструментов реализации

| Задача | Выбранный инструмент | Рассмотренные альтернативы | Обоснование выбора |
|---|---|---|---|
| Получение результатов из LIS | Опрос REST API LIS адаптером по отметке времени с перекрытием окна | Передача из LIS в адаптер по инициативе LIS; CDC из БД LIS; файлы по FTP | Опрос оставляет повторы под контролем адаптера: при недоступности LIS отметка не сдвигается, и данные дочитываются. Передача по инициативе LIS держится на механизме, который сейчас реализован Perl-коннектором без повторов. CDC привязывает интеграцию к схеме БД. Файлы по FTP теряются (INT-002) |
| Публикация событий из адаптера и CRM | Transactional Outbox с relay, опрашивающим таблицу outbox | Debezium CDC по таблице outbox; публикация в брокер сразу после коммита | Relay с опросом не требует Kafka Connect и проще в эксплуатации, а задержка опроса таблицы несопоставимо меньше интервала забора из LIS. Публикация сразу после коммита является антипаттерном «Двойная запись»: сбой между операциями теряет событие |
| Брокер событий | Apache Kafka, топики `lab-results` и `patient-results` | RabbitMQ | Kafka хранит события и позволяет перечитать их после сбоя потребителя, pull-модель защищает CRM от всплеска, разные группы потребителей читают топик независимо. RabbitMQ удаляет подтверждённые сообщения и не даёт повторного чтения |
| Ключ партиционирования | ID результата для `lab-results`, ID пациента для `patient-results` | Без ключа; единый ключ на все события | Ключ по ID результата сохраняет порядок версий одного результата (исходный и исправленный). Без ключа версии могут обработаться в обратном порядке. Единый ключ сводит обработку к одной партиции и лишает масштабирования |
| Обработка ошибок у потребителя | Неблокирующая переобработка: retry-топик и DLQ `lab-results.dlq` с алертом | Блокирующие повторы в основном потоке | Блокирующий повтор останавливает всю партицию, и остальные результаты ждут, что соответствует ситуации «застряло в очереди» (INT-011). Retry-топик выносит сбойное событие из основного потока |
| Защита от дублей | Upsert по паре «ID результата + версия», журнал обработанных eventId | Exactly-once средствами Kafka Transactions | При идемпотентном upsert повторная доставка не меняет данные, поэтому at-least-once достаточно. Exactly-once усложняет реализацию без выигрыша для этого потока |
| Сигнал пациенту о готовности | Push по событию «РезультатДоступен», которое публикует CRM после сохранения результата | Уведомления читают `lab-results` параллельно с CRM | При параллельном чтении push может прийти раньше, чем CRM сохранит результат, и пациент увидит пустой экран. Событие от CRM гарантирует, что данные уже доступны |
| Доставка данных в приложение | Запрос приложения через API Gateway в CRM с чтением из реплики | Результат в теле push; постоянное соединение приложения с сервером (WebSocket, SSE) | В теле push медицинские данные ушли бы внешнему провайдеру уведомлений. Постоянные соединения для 50 тыс. пользователей избыточны для события, которое у пациента происходит редко |
| Отправка уведомлений | Существующие Уведомления: приоритетная очередь push в RabbitMQ, резервный канал SMS или email | Отправка push напрямую из CRM | Уведомления уже владеют каналами и провайдерами. Приоритетная очередь отделяет уведомления о результатах от рекламных рассылок |
| Контроль доставки | Метрика свежести, consumer lag, размер DLQ, суточная сверка, панель доставки в Адаптере LIS, сквозной traceId | Мониторинг только технических ошибок | Мониторинг ошибок не обнаруживает результат, который не был забран вовсе. Сверка и метрика свежести ловят такие пропуски, панель даёт лаборантам и поддержке возможность повторить доставку |
