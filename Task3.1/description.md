# Задание 3.1. Надёжная поставка результатов анализов в мобильное приложение: описание решения

## Исходная ситуация

Результаты анализов передаются из LIS в CRM Perl-коннектором, у которого нет владельца и документации. При сбое коннектор не переотправляет данные, и восстановление выполняется вручную (SD-005, отзыв Алексея). Задержка передачи достигает двух часов (INT-002, отзывы Елены и Анны). Дублирование XML-файлов приводит к дублям анализов в CRM (INT-008). Данные застревают в очереди, и CRM показывает неактуальные результаты (INT-011). Лаборанты видят, загрузились ли данные, но не могут повлиять на загрузку. У пациентов нет доступа к результатам онлайн: контакт-центр пересылает скриншоты и письма (отзывы Олега и Анны).

## Требования к решению

| Требование | Целевое значение |
|---|---|
| Гарантированная доставка | Каждый результат доставляется в CRM и приложение без потерь и без дублей. Для каждого сценария сбоя предусмотрен механизм восстановления без ручной перевыгрузки |
| Задержка | Не более 2 минут от статуса «готов» в LIS до появления результата в приложении (сейчас до 2 часов) |
| Пиковая нагрузка | Утренний всплеск после ночной загрузки результатов обрабатывается без потерь и без деградации CRM. Волна чтений после рассылки push не перегружает CRM |
| Простота эксплуатации | Сбой доставки обнаруживается автоматически. Повторить доставку конкретного результата может лаборант или сотрудник поддержки без участия разработчика |

Поток начинается с момента, когда результат получил в LIS статус «готов». Загрузка файлов с лабораторного оборудования в LIS выполняется пакетным потоком с мониторингом, автоматическим повтором сбойных пакетов и алертингом и в этот поток не входит.

## Выбранное решение

Результаты доставляются событийно через брокер Apache Kafka. Используются Transactional Outbox, идемпотентные потребители, неблокирующая переобработка ошибок с Dead Letter Queue и суточная сверка с LIS. Пациент получает push-уведомление о готовности, а сами результаты загружает в приложении запросом через API Gateway.

### Участники потока

| Компонент | Роль в потоке |
|---|---|
| LIS | Источник результатов. Предоставляет REST API для чтения результатов |
| Адаптер LIS | Забирает результаты из LIS, отсекает дубли, сохраняет результат и событие в одной транзакции, публикует события. Содержит панель доставки для лаборантов и поддержки |
| Kafka, топик `lab-results` | Хранит события «РезультатГотов». Ключ партиционирования — ID результата |
| CRM | Сохраняет результат для врачей и пациентов, публикует событие «РезультатДоступен» |
| Kafka, топик `patient-results` | Хранит события «РезультатДоступен». Ключ партиционирования — ID пациента |
| Уведомления | Формирует и отправляет пациенту push, при отсутствии push-токена отправляет SMS или email |
| API Gateway | Принимает запрос приложения, проверяет JWT и лимиты, маршрутизирует запрос в CRM |
| Мобильное приложение | Показывает пациенту его результаты |

### Шаги потока

1. **Забор из LIS.** Адаптер LIS раз в минуту запрашивает у REST API LIS результаты, изменённые после отметки последнего забора. Окно запроса перекрывается с предыдущим, чтобы не пропустить результаты с одинаковой отметкой времени. Повторы, возникающие из-за перекрытия, отсекаются на следующем шаге. Отметка сдвигается только после успешного сохранения полученной порции.
2. **Дедупликация.** Адаптер проверяет пару «ID результата + версия» по журналу обработанных. Уже обработанная версия пропускается. Исправленный результат получает новую версию и проходит дальше.
3. **Сохранение с событием.** В одной транзакции адаптер сохраняет результат и событие «РезультатГотов» в таблицу outbox. Результат и событие не могут разойтись.
4. **Публикация.** Relay читает таблицу outbox и публикует события в топик `lab-results` с подтверждением от всех реплик брокера и идемпотентным продюсером. Событие помечается опубликованным только после подтверждения брокера.
5. **Сохранение в CRM.** Группа потребителей CRM читает `lab-results` и выполняет идемпотентный upsert результата по ID и версии. В той же транзакции CRM записывает событие «РезультатДоступен» в свою таблицу outbox. Offset фиксируется после коммита транзакции.
6. **Сигнал пациенту.** Уведомления читают `patient-results`, отсекают повторы по eventId и ставят задачу в приоритетную push-очередь RabbitMQ. Push содержит только сообщение «Результаты готовы» и ссылку на результат, медицинские данные в нём не передаются. Если у пациента нет push-токена, отправляется SMS или email.
7. **Выдача в приложение.** По push или при открытии приложение запрашивает результаты через API Gateway. Идентификатор пациента берётся из JWT, поэтому пациент получает только свои результаты. CRM отдаёт данные из реплики БД. Запрос конкретного результата по ссылке из push при отсутствии записи в реплике читается из основной БД.

Врачи получают результаты в CRM по тому же потоку, поэтому решение устраняет и неактуальность данных у врачей.

## Гарантия доставки

| Сценарий сбоя | Механизм | Результат |
|---|---|---|
| LIS недоступна или отвечает ошибкой при опросе | Повтор с экспоненциальной задержкой, Circuit Breaker, отметка забора не сдвигается | После восстановления LIS адаптер дочитывает все результаты с последней отметки |
| Результат пропущен при заборе | Суточная сверка списка результатов за день в LIS и в адаптере, дозагрузка расхождений | Пропуск обнаруживается и устраняется в пределах суток без ручной работы |
| Адаптер остановился между сохранением результата и публикацией | Transactional Outbox | Relay публикует событие после перезапуска |
| Kafka недоступна | События накапливаются в таблице outbox | Публикация продолжается после восстановления брокера |
| CRM недоступна или обрабатывает медленно | События хранятся в Kafka, CRM читает с последнего зафиксированного offset | CRM догоняет поток без потерь |
| Конкретное событие не обрабатывается | Повторы через retry-топик, после исчерпания попыток событие уходит в `lab-results.dlq`, срабатывает алерт | Основной поток не блокируется. Событие повторно отправляется из DLQ после устранения причины |
| Повторный файл, повторная доставка события | Дедупликация по ID и версии в адаптере, идемпотентный upsert в CRM, дедупликация по eventId в Уведомлениях | Дубли результатов и повторные push исключены |
| Push не доставлен | Durable-очередь и DLQ в Уведомлениях | Уведомление повторяется. Результат доступен в приложении независимо от push |
| Push отправлен раньше, чем результат сохранён в CRM | Push формируется по событию «РезультатДоступен», которое CRM публикует после сохранения | Пациент не открывает пустой экран результатов |

Для всех событий принята гарантия at-least-once с идемпотентными потребителями. Повторная доставка не меняет состояние, поэтому exactly-once не требуется.

## Задержка

Задержка определяется интервалом опроса LIS (1 минута) и временем прохождения события через Kafka, CRM и Уведомления, которое измеряется секундами. Интервал опроса является параметром адаптера и может быть уменьшен без изменения архитектуры, если нагрузка на REST API LIS это допускает.

## Пиковая нагрузка

Утренний всплеск результатов принимает Kafka. Потребители читают события в своём темпе (pull-модель), поэтому всплеск не перегружает CRM. Пропускная способность CRM-потребителя масштабируется добавлением экземпляров в группу потребителей в пределах числа партиций топика. Число партиций выбирается по пиковому объёму результатов с запасом на рост.

Волна чтений после рассылки сглаживается тремя механизмами. Очередь push в Уведомлениях отправляет сообщения с контролируемой скоростью, и пациенты открывают приложение не одновременно. Чтение результатов выполняется из реплики БД CRM и не мешает работе сотрудников. API Gateway ограничивает частоту запросов на пользователя.

## Эксплуатация и контроль

| Средство | Что показывает | Кто использует |
|---|---|---|
| Метрика свежести | Время от статуса «готов» в LIS до сохранения результата в CRM. Алерт при превышении 2 минут | Дежурная служба |
| Отставание потребителей (consumer lag) | Сколько событий в `lab-results` и `patient-results` ещё не обработано | Дежурная служба |
| Размер DLQ | Число событий, не обработанных после всех попыток. Алерт при появлении события | Дежурная служба |
| Отчёт суточной сверки | Расхождения между LIS и адаптером и результат их дозагрузки | Дежурная служба, поддержка |
| Панель доставки в Адаптере LIS | Статус доставки каждого результата: забран, опубликован, сохранён в CRM, уведомление отправлено. Кнопка повторной отправки | Лаборанты, сотрудники поддержки и контакт-центра |
| Сквозной traceId | Прохождение конкретного результата через адаптер, Kafka, CRM и Уведомления | Разработчики и дежурная служба при разборе инцидентов |

Повторная отправка из панели безопасна: все потребители идемпотентны, поэтому повтор не создаёт дублей.
