# Задание 4.3. Политики Rate Limiting

Ограничения применяются на внешнем API Gateway. Счётчики хранятся в общем Redis, поэтому лимит действует суммарно для всех экземпляров шлюза, а не для каждого отдельно.

## Таблица политик

| Тип запроса | Лимит | Действие при превышении |
|---|---|---|
| **Поиск врачей** (`GET /api/v1/doctors`, публичный, без токена)<br>Ключ ограничения — IP-адрес клиента<br>Алгоритм — Token Bucket | **30 запросов в минуту** с одного IP-адреса, допустимый всплеск — 10 запросов подряд.<br>Дополнительный рубеж: **300 запросов в минуту** с одной подсети /24, чтобы ограничить обращения из мобильных сетей с общим адресом.<br>Глобальный предел метода: **500 запросов в секунду** суммарно | Ответ `429 Too Many Requests` с заголовком `Retry-After` и телом в едином формате ошибки (`code`, `message`, `traceId`).<br>В каждом успешном ответе возвращаются заголовки `X-RateLimit-Limit`, `X-RateLimit-Remaining` и `X-RateLimit-Reset`, чтобы приложение снижало частоту до срабатывания лимита.<br>При устойчивом превышении дольше 5 минут адрес передаётся в правила WAF и блокируется на 15 минут.<br>При достижении глобального предела метода включается отдача результатов из кеша: выдача может быть неактуальной, но метод остаётся доступным |
| **Создание записи к врачу** (`POST /api/v1/appointments`, требует токена)<br>Ключ ограничения — идентификатор пациента из токена (`sub`)<br>Алгоритм — Token Bucket | **10 запросов в минуту** на пациента, допустимый всплеск — 3 запроса подряд.<br>Отдельный суточный предел: **50 запросов в сутки** на пациента.<br>Повторные запросы с тем же значением `Idempotency-Key` в пределах минуты не расходуют лимит, поскольку являются повторами одной операции, а не новыми попытками записи | Ответ `429 Too Many Requests` с заголовком `Retry-After`. Приложение обязано выполнять повтор с экспоненциальной задержкой, а не показывать пациенту ошибку немедленно.<br>При превышении суточного предела запись через приложение приостанавливается, пациенту предлагается обратиться в контакт-центр, событие передаётся в платформу наблюдаемости.<br>При превышении более трёх раз за час учётная запись помечается для проверки службой безопасности: такая частота не соответствует поведению пациента |

## Обоснование параметров

### Поиск врачей

Метод публичный, поэтому ключом ограничения может быть только сетевой адрес: токена в запросе нет. Это самый слабый вид ключа, потому что адрес меняется, а за одним адресом может находиться много легитимных пользователей — например, клиенты одного мобильного оператора. По этой причине лимит на адрес сочетается с лимитом на подсеть и глобальным пределом метода, а основную защиту от распределённых атак обеспечивает уровень CDN и WAF перед шлюзом.

Значение 30 запросов в минуту выбрано от поведения пациента: за минуту человек выполняет несколько поисков по специальности, клинике или фамилии врача, но не десятки. Всплеск в 10 запросов покрывает быстрый перебор фильтров на экране поиска.

Полная блокировка метода при достижении глобального предела нежелательна: поиск врачей — это витрина, и её недоступность видна всем, включая пациентов, которые ещё не зарегистрированы. Поэтому вместо отказа включается отдача данных из кеша.

### Создание записи

Запрос изменяет состояние, затрагивает слот, лабораторное окно и деньги пациента, поэтому лимит здесь жёстче. Ключом служит идентификатор пациента из токена: он не подменяется и не зависит от сети, через которую работает приложение.

Значение 10 запросов в минуту заведомо превышает нормальное поведение: пациент оформляет одну запись за раз. Запас нужен на случай, когда пациент оформляет записи для нескольких членов семьи подряд или исправляет неверно выбранное время.

Повторы с тем же ключом идемпотентности выведены из-под лимита осознанно. Приложение выполняет повторы при обрыве связи, и наказывать его кодом 429 за устойчивость к сетевым сбоям неправильно: такой повтор не создаёт новую запись, а запрашивает результат уже начатой операции.

## Алгоритм ограничения

Для обоих методов выбран Token Bucket. Он допускает короткий всплеск и ограничивает среднюю скорость, что соответствует реальному поведению мобильного клиента: пациент совершает серию действий на экране, затем пауза. Fixed Window пропустил бы двойной поток на стыке двух окон, что при жёстком лимите на создание записи означало бы до 20 запросов подряд. Sliding Window даёт более точный подсчёт, но его точность нужна там, где по числу запросов выставляется счёт, чего в этом сценарии нет.

## Место в эшелонированной защите

| Рубеж | Что делает |
|---|---|
| CDN | Отсекает объёмные распределённые атаки до попадания трафика в инфраструктуру |
| WAF | Блокирует атаки уровня приложения и адреса, переданные шлюзом как нарушители |
| API Gateway | Применяет политики из таблицы, проверяет токен, отсекает неаутентифицированные запросы к защищённым методам |
| Сервисы | Защищены таймаутами, Circuit Breaker и собственными ограничениями темпа к внешним системам, в том числе к 1С |

Rate limiting на шлюзе не заменяет внешний рубеж: ограничение по адресу не помогает против атаки с тысяч разных источников, поскольку каждый из них по отдельности остаётся в пределах лимита.

## Контроль

| Метрика | Назначение |
|---|---|
| Число ответов 429 по методам | Показывает, не задушены ли легитимные пациенты слишком строгим лимитом |
| Доля пациентов, достигших лимита создания записи | При росте доли лимит пересматривается: норма — единичные случаи |
| Число заблокированных адресов | Показывает активность атак на публичные методы |
| Доля запросов поиска, обслуженных из кеша | Показывает, как часто срабатывает глобальный предел метода |
