# Задание 4.3. Меры защиты каналов передачи данных

Меры сгруппированы по участкам пути данных: от устройства пациента до внутренних систем.

## 1. Канал «мобильное приложение — периметр»

| Мера | Содержание | Что предотвращает |
|---|---|---|
| **Только TLS 1.3, TLS 1.2 как минимально допустимый** | Соединения по HTTP не обслуживаются. Соединения по протоколам ниже TLS 1.2 отклоняются. Разрешены наборы шифров с прямой секретностью | Чтение персональных и медицинских данных при перехвате трафика, в том числе в открытых сетях Wi-Fi |
| **HSTS** | Заголовок `Strict-Transport-Security` с длительным сроком и включением поддоменов | Понижение соединения до HTTP при первом обращении или по подставленной ссылке |
| **Закрепление сертификата (certificate pinning)** | Приложение доверяет только сертификатам «Здоровье+», проверяя отпечаток открытого ключа. Закрепляются два ключа: действующий и резервный, чтобы плановая смена сертификата не сломала приложение | Перехват трафика через подставленный корневой сертификат, установленный на устройстве пациента |
| **Токен только в заголовке** | Токен доступа передаётся в заголовке `Authorization`. Передача токена в параметрах адреса запрещена | Попадание токена в журналы прокси и серверов, историю браузера и заголовок `Referer` |
| **Запрет чувствительных данных в адресе запроса** | Номер полиса, идентификатор пациента, состав анализов передаются в теле запроса или извлекаются из токена | Утечка данных через журналы, которые обычно пишут полный адрес запроса |
| **Защита от повторного воспроизведения** | Изменяющие запросы содержат `Idempotency-Key`, время жизни токена доступа ограничено 15 минутами | Повторная отправка перехваченного запроса злоумышленником |

## 2. Периметр

| Мера | Содержание | Что предотвращает |
|---|---|---|
| **CDN с защитой от DDoS** | Фильтрация объёмного трафика до попадания в инфраструктуру | Недоступность приложения при распределённой атаке |
| **WAF** | Блокировка атак уровня приложения: внедрение SQL-кода, межсайтовый скриптинг, обход путей | Эксплуатацию уязвимостей, подобных обнаруженной инъекции в поиске пациента |
| **Единая точка входа** | Внутренние сервисы не имеют публичных адресов. Трафик из интернета попадает только на API Gateway | Прямое обращение к сервисам в обход проверки токена и ограничения частоты |
| **Rate limiting на шлюзе** | Политики по типам запросов, счётчики в общем хранилище | Перебор данных и перегрузку сервисов |

## 3. Канал «шлюз — внутренние сервисы» и межсервисные вызовы

| Мера | Содержание | Что предотвращает |
|---|---|---|
| **mTLS между сервисами** | Обе стороны предъявляют сертификаты. Сервис принимает вызовы только от сервисов с действующим сертификатом, выпущенным внутренним удостоверяющим центром | Подключение постороннего процесса к внутреннему сервису при получении доступа к сети, атаку «человек посередине» внутри контура |
| **Короткоживущие сертификаты и автоматическая ротация** | Срок действия измеряется часами, выпуск и обновление автоматизированы через централизованное управление секретами | Длительное использование скомпрометированного сертификата |
| **Сегментация сети** | Доступ к 1С, базам данных, брокеру и Redis разрешён только тем сервисам, которым он нужен по архитектуре | Горизонтальное перемещение злоумышленника внутри контура после компрометации одного сервиса |
| **Идентификатор пациента только из токена** | Сервисы получают идентификатор пациента во внутреннем заголовке, заполняемом шлюзом после проверки подписи токена, и не принимают его из параметров запроса | Обращение к чужим медицинским данным подстановкой чужого идентификатора |
| **Проверка прав на уровне данных** | Каждый сервис проверяет принадлежность запрошенной сущности пациенту из контекста запроса, а не полагается только на проверку токена на шлюзе | Доступ к чужой записи по угаданному или подсмотренному идентификатору |

## 4. Защита от внедрения кода и работа с данными

| Мера | Содержание | Что предотвращает |
|---|---|---|
| **Параметризованные запросы к базам данных** | Обращения к базам строятся через подготовленные выражения. Конкатенация пользовательского ввода в текст запроса запрещена | Внедрение SQL-кода. WAF служит дополнительным рубежом, но не заменяет исправление в коде |
| **Валидация входных данных по схеме** | Шлюз проверяет запрос на соответствие спецификации: типы, форматы, диапазоны, перечисления, максимальные размеры тела | Передачу некорректных и намеренно искажённых данных в сервисы |
| **Кодирование вывода** | Данные, введённые пользователями, экранируются при отображении в веб-интерфейсах | Межсайтовый скриптинг в интерфейсах сотрудников |
| **Ограничение объёма выдачи** | Пагинация с максимальным размером страницы, ограничение диапазона дат в фильтрах | Массовое извлечение данных через легитимный метод |

## 5. Хранение и обработка на устройстве

| Мера | Содержание | Что предотвращает |
|---|---|---|
| **Токены в защищённом хранилище устройства** | Keychain на iOS, Keystore на Android. Доступ подтверждается биометрией или кодом устройства | Извлечение токенов из файлов приложения на скомпрометированном устройстве |
| **Отсутствие медицинских данных в кеше приложения** | Результаты анализов и сведения о записях не сохраняются в незашифрованных файлах и не попадают в резервные копии устройства | Чтение медицинских данных при получении доступа к файловой системе устройства или к резервной копии |
| **Скрытие содержимого при сворачивании** | Экраны с медицинскими данными скрываются в списке запущенных приложений | Просмотр данных посторонним при передаче устройства в чужие руки |
| **Отсутствие данных в push-уведомлениях** | Push содержит только факт события: «результаты готовы», «запись подтверждена». Сами результаты и диагнозы в уведомление не помещаются | Передачу медицинских данных внешнему провайдеру уведомлений и показ их на заблокированном экране |

## 6. Наблюдаемость и реакция

| Мера | Содержание | Что предотвращает |
|---|---|---|
| **Маскирование в журналах** | Токены, номера полисов, результаты анализов, платёжные реквизиты не попадают в журналы. Записывается идентификатор пациента и traceId | Превращение системы журналов во вторую копию медицинской базы, доступную более широкому кругу сотрудников |
| **Журнал доступа к медицинским данным** | Фиксируется, кто и к каким данным обращался, с сохранением записей | Незаметный доступ сотрудника к данным пациентов вне рабочих задач, разбор инцидентов подобных обращению о чужом пациенте |
| **Оповещения о подозрительной активности** | Массовые запросы к данным разных пациентов от одной учётной записи, всплеск ответов 401, необычная география обращений | Длительную незамеченную эксплуатацию уязвимости |
| **Ротация и хранение секретов** | Ключи, пароли и сертификаты хранятся в централизованном хранилище секретов, а не в конфигурационных файлах и репозиториях | Утечку доступа через исходный код или образы контейнеров |

## Обязательный минимум для запуска

Меры, без которых запуск мобильного приложения не выполняется:

1. TLS 1.2 и выше на всех внешних соединениях, HSTS.
2. Закрепление сертификата в приложении.
3. mTLS между шлюзом и внутренними сервисами.
4. Устранение внедрения SQL-кода в коде, а не только правилом WAF.
5. Идентификатор пациента исключительно из проверенного токена и проверка принадлежности данных на уровне сервиса.
6. Токены в защищённом хранилище устройства, медицинские данные вне push-уведомлений.
7. Маскирование чувствительных данных в журналах.

Остальные меры внедряются в первые месяцы эксплуатации по мере накопления данных о фактическом профиле нагрузки и обращениях.
