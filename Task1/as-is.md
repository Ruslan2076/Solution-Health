# Задание 1. Анализ текущей интеграционной архитектуры «Здоровье+»

Анализ выполнен по артефактам кейса: контекстная диаграмма C4 (Level 1), таблица технологического стека, выгрузка Jira (INT-xxx), тикеты Service Desk (SD-xxx), отзывы сотрудников и новости о компании. Для каждой проблемы указано влияние на MVP (запись, оплата, уведомления; 500 одновременных пользователей) и на финальное решение (50 тыс. пользователей, p99 < 1 с, доступность 99,95%, горизонтальное масштабирование). Проблемы упорядочены по влиянию на MVP.

## Выявленные проблемы

| Проблема | Признаки | Влияние на приложение |
|---|---|---|
| **1. Нет точки входа для мобильного клиента.** Все системы вызывает только веб-портал, синхронно. API Gateway, rate limiting и единой обработки ошибок нет. API для пациента к результатам анализов нет: они доступны только сотрудникам в CRM. Запись по ДМС с оплатой затрагивает 1С, Расписание и платёжный шлюз синхронными вызовами; при последовательном выполнении это антипаттерн «Синхронная цепочка вызовов» | C4: все связи к системам идут от веб-портала (запись/слоты, проверка полиса, оплата, синхронизация с CRM), все синхронные<br>INT-010 (Epic, Critical): API Gateway с rate limiting и идемпотентностью только запланирован<br>Отзыв Алексея: rate limiting нет<br>Отзыв Олега: веб-портал не справляется; доступ к CRM дать нельзя, результаты пересылают скриншотами<br>Отзыв Анны: MVP третий месяц не выходит за тестовые стенды; результаты доступны только сотрудникам в CRM<br>SD-004 | MVP: приложению остаётся подключаться либо через перегруженный портал, либо напрямую к сервисам (антипаттерн «Прямой доступ в обход Gateway»). Всплеск запросов из приложения (рекламная кампания, пуш об акции) без ограничений доходит до 1С и Расписания. Время отклика записи определяется самым медленным звеном цепочки.<br>Финал: при такой схеме недостижимы p99 < 1 с и горизонтальное масштабирование |
| **2. Оплата: синхронный вызов внешнего шлюза без обработки неопределённого исхода.** При таймауте деньги списываются, а статус платежа в системе не фиксируется. Таймаут есть (около 10 с по SD-004), но после него исход платежа не выясняется. Двойные списания указывают на отсутствие идемпотентности платёжной операции (антипаттерн «Отсутствие идемпотентности»); точная причина в тикете пока не установлена | INT-001 (Blocker): при таймауте деньги списываются, статус не фиксируется<br>SD-004: тестовая версия приложения зависает на оплате на 10 с, затем ошибка<br>SD-009 (In Progress): двойное списание<br>Отзыв Марины: после акции платежи падали, деньги списывались дважды, акцию свернули<br>C4: «Оплата (синхронно) [REST]»<br>Стек: платёжный шлюз, синхронный REST API | MVP: оплата входит в ядро MVP, дефект уже воспроизведён на тестовой версии приложения. Пациент видит ошибку при списанных деньгах, повторяет оплату и получает двойное списание, затем звонит и ждёт возврата.<br>Финал: бизнес опасается запускать предложения с оплатой, поэтому под угрозой цель по росту среднего чека за счёт дополнительных услуг в приложении |
| **3. Процесс «запись + оплата» не согласован между системами.** Запись создаётся в Расписании, платёж проходит во внешнем шлюзе, связь между ними теряется. Координации шагов (Saga) и компенсирующих действий (автоотмена записи, возврат платежа) нет, возвраты выполняются вручную. Какой компонент сейчас связывает шаги, в артефактах не описано; по C4 оба вызова выполняет веб-портал | SD-002 (Open): пациент оплатил, подтверждение не пришло, в логах «Booking not found для paymentID»<br>Новость (Новосибирск, 15.03): оплаченные записи теряются, деньги не возвращаются<br>Отзыв Олега: люди платят, а слота нет; деньги возвращаются неделями; растёт число эскалаций<br>INT-001 | MVP: ключевой сценарий может закончиться списанными деньгами без визита. По словам руководителя контакт-центра, каждый второй звонок связан с двойными записями или потерей подтверждения. Если приложение будет работать на тех же бэкендах, эти звонки сохранятся и цель снижения нагрузки на колл-центр на 30% не будет достигнута |
| **4. Нет идемпотентности в API Расписания.** Повторный POST создаёт вторую запись: сервис не отличает повторный запрос от нового, Idempotency-Key отсутствует (антипаттерн «Отсутствие идемпотентности») | INT-005 (Blocker): дубли записей при повторных POST<br>SD-003: двойное нажатие «Записаться» создало две записи<br>Отзыв Дмитрия: повторные запросы не различаются, идемпотентности нет<br>Отзыв Олега: двойные записи<br>INT-010: идемпотентность только запланирована | MVP: в мобильном клиенте повторные запросы неизбежны: двойной тап, повторная отправка при обрыве связи или таймауте, автоматический retry. Дубли занимают слоты и снижают реальную ёмкость расписания. Без идемпотентности нельзя безопасно включить retry ни в приложении, ни на шлюзе, то есть блокируется внедрение остальных механизмов отказоустойчивости |
| **5. База данных Расписания не выдерживает пиковой нагрузки.** Чтение слотов и запись идут в одну PostgreSQL. В часы пик возникают блокировки таблицы слотов, реплики для чтения нет. Изменения расписания врачами применяются с задержкой или теряются, поэтому часть записи ведётся в Excel вне системы | INT-009 (Task, Major): репликация БД для чтения из-за блокировок<br>Отзыв Дмитрия: блокировки таблицы слотов в часы пик, масштабирование чтения не сделано, изменения врачей вносятся с задержкой или не фиксируются<br>Отзыв Олега: врачам медленно управлять расписанием, изменения иногда не сохраняются<br>Новость (Екатеринбург, 01.04): врачи ведут запись в Excel, ручной ввод занимает до 2 ч в день<br>Новость (Новосибирск, 15.03): четвёртый сбой онлайн-записи за месяц | MVP: пиковое время приложения (вечера, выходные) совпадает с пиком блокировок, а просмотр свободных слотов будет одним из самых частых запросов. Возможны медленные ответы и ошибки при 500 одновременных пользователях. Пациенту могут показываться слоты, которых фактически нет (изменение не сохранилось или запись ведётся в Excel).<br>Финал: 50 тыс. пользователей и p99 < 1 с недостижимы на одной БД без реплик |
| **6. Брокер уведомлений перегружается, его лимиты неизвестны.** В пиках очереди RabbitMQ разрастаются, при превышении лимита очередь падает с ошибкой 404, уведомления теряются. Лимиты не задокументированы. Сервис уведомлений использует брокер совместно с другими потоками; конфигурация очередей, DLQ и prefetch в артефактах не описана | SD-006: пуш на Android не пришёл, очередь RabbitMQ переполнилась из-за пиковой нагрузки<br>Отзыв Елены: RabbitMQ «держится на честном слове», пики вечером в понедельник создают огромные очереди, после превышения лимита очередь упала с 404 и пациенты не получили уведомления о записях; сервис уведомлений «висит на этом же RabbitMQ»<br>INT-004: лимиты RabbitMQ не задокументированы<br>C4: Уведомления на RabbitMQ | MVP: пуш о статусе записи входит в MVP, а пиковая нагрузка MVP (вечера, выходные) совпадает с пиком брокера. Потерянное подтверждение записи превращается в звонок в клинику. Рассылки об акциях через тот же канал добавят объём в тот же пик и могут задержать пуши о записи |
| **7. 1С: Полисы работает на пределе пропускной способности.** Проверка полиса выполняется синхронно по HTTP. При нагрузке выше 50 rps 1С отвечает 503, иногда отвечает дольше 30 с или возвращает null, который трактуется как «полис недействителен». Rate limiting перед 1С нет, восстановление выполняется перезапуском службы. Временное решение (нет ответа 5 с, полис считается валидным) бизнесом не согласовано | INT-003 (Critical): проверка полиса падает с 503 при > 50 rps<br>SD-001: ответ дольше 30 с, помогает только перезагрузка службы<br>SD-008: 1С вернул null, пациенту показано «Полис недействителен», повтор через 5 мин успешен<br>Отзыв Алексея: rate limiting нет, при небольшом всплеске 1С перестаёт отвечать; временное решение с 5 с бизнес не подписывает<br>Отзыв Анны: онлайн-проверка часто не находит полис, бизнес теряет клиентов<br>C4: «Проверка полиса (синхронно) [HTTP]» | MVP: если запись по ДМС в приложении пойдёт через проверку полиса, как сейчас на портале, вся ДМС-запись упрётся в предел 50 rps. Ложный отказ «полис недействителен» приводит к звонку или уходу пациента. Включение несогласованного временного решения создаёт риск оказать услугу по невалидному полису.<br>Финал: сценарий «управление полисами ДМС» при 50 тыс. пользователей упирается в этот предел |
| **8. Контракт 1С нестабилен.** Формат ответа меняется без уведомления потребителей. Зафиксированного контракта и версионирования нет. Ответ null вместо кода ошибки не имеет определённой семантики. Слоя, изолирующего потребителей от изменений 1С, нет: смена формата сразу ломает интеграцию | Отзыв Алексея: контракт меняется без уведомлений, вместо JSON стали возвращать XML, интеграция сломалась<br>SD-008: 1С вернул null | Любое изменение на стороне 1С одновременно ломает ДМС-запись и работу с полисами в приложении во всех четырёх городах, а обнаруживается это по жалобам пациентов (см. проблему 12) |
| **9. Загрузка результатов с оборудования в LIS ненадёжна.** Пакетная загрузка по FTP падает (ошибка 425, таймауты, потеря соединения), автоматических повторов нет, восстановление ручное. Ночной сбой обнаруживается только утром | INT-002 (Major): загрузка через FTP падает с 425, требуется ручное восстановление<br>SD-005: FTP-скрипт падал по таймауту, запускали вручную<br>Отзыв Елены: потеря соединения, таймауты, никаких автоматических повторов; если скрипт упал ночью, утром пациенты без анализов<br>Отзыв Анны: автоматическая загрузка с оборудования иногда сбоит, врач не видит анализы | Финал (сценарий «результаты анализов»): приложение показывает, что результатов нет, хотя анализ готов, и пациент звонит в клинику, то есть делает то, от чего приложение должно избавить. Если пуш о готовности анализов войдёт в MVP, он будет приходить с опозданием или не придёт |
| **10. Интеграция LIS → CRM теряет, дублирует и задерживает данные.** Передача идёт через REST API коннектором на старом Perl без владельца и документации; при сбое коннектор не переотправляет данные. Дублирование XML-файлов приводит к дублям анализов в CRM: дедупликации на стороне получателя нет. Данные застревают в очереди, которая не отражена на диаграмме C4. Задержка передачи достигает 2 ч | INT-008 (Major): дубли XML-файлов, в CRM попадают дубли анализов<br>INT-011 (Major): LIS передал данные, CRM не обновилась, данные застряли в очереди<br>INT-002: задержка передачи в CRM до 2 ч<br>SD-005: REST-коннектор не переотправил данные<br>Отзыв Алексея: коннектор на Perl, никто не сопровождает, при сбоях перезапуск вручную, документации нет<br>Отзыв Елены: задержка до 2 ч, своевременность гарантировать нельзя<br>Отзыв Анны: задержка на несколько часов<br>C4: LIS → CRM по REST API (JSON), очередь на диаграмме отсутствует | Пациент увидит в приложении дубли, устаревшие или отсутствующие результаты анализов, что для медицинских данных создаёт риск неверной интерпретации. Пока своевременность передачи не гарантирована, срок появления результатов в приложении пациенту обещать нельзя |
| **11. Уязвимости безопасности в текущем контуре.** В поиске пациента на веб-портале есть SQL-инъекция. Есть подозрение на подмену сессии: врач видит чужого пациента, расследование не завершено. Механизм аутентификации и авторизации пациентов в артефактах не описан | INT-006 (Major): SQL-инъекция в поле поиска пациента<br>SD-007 (In Progress): врач видит чужого пациента, возможна подмена сессии | Приложение открывает внешний доступ к результатам анализов, полисам и платежам через те же системы. Если аутентификация приложения повторит механизм портала, дефект SD-007 перейдёт в приложение. Утечка медицинских и персональных данных несёт репутационные и юридические последствия |
| **12. Нет наблюдаемости, восстановление ручное.** Распределённой трассировки нет, корень сбоя приходится искать вручную по логам отдельных систем. Сбои первыми замечают пациенты и сотрудники, штатный способ восстановления — ручной перезапуск | INT-007 (Critical): отсутствие distributed tracing, сложно найти корень сбоя<br>SD-002 (Open): связь paymentID и записи выясняется по логам<br>SD-001, SD-005, INT-002: ручное восстановление<br>Отзыв Алексея: при сбоях перезапускаем вручную<br>Отзыв Анны: «Всё непредсказуемо»<br>Новость (Новосибирск, 15.03): сбои клиника объясняет техническими работами | Инцидент в приложении проходит через портал, Расписание, платёжный шлюз, 1С и брокер, и без трассировки его долго локализуют.<br>Финал: доступность 99,95% допускает около 22 мин простоя в месяц (0,05% от 30 суток). Один ночной сбой, обнаруженный утром, выбирает этот бюджет целиком |
